    Packaging and versioning¶

    The two crates of this repository are prepared as independent Cargo packages (issue #4). They are not published to crates.io: registry publication is a separate step. The first GitHub release is prepared as v0.1.0 against Core v0.8.0 (#33). The packaging validation records the local results.

    Package identities¶

    Crate Role Native metadata Categories
    opentlv-sys Raw C FFI declarations, Core selection and native linking links = "tlv", build.rs external-ffi-bindings
    opentlv Safe Rust API build.rs, which only forwards the selected Core tree to the tests parser-implementations, encoding, api-bindings

    The crate names, descriptions, links value, Cargo features and their defaults are unchanged from the migration baseline; the opentlv build script was added by the standalone build.

    Both crates inherit this metadata from [workspace.package] in the root Cargo.toml:

    Field Value
    version 0.1.0
    edition 2021
    rust-version 1.82
    license MIT
    repository https://github.com/OpenTLV/opentlv-rust
    keywords tlv, ber, asn1, emv, parser

    Each crate has its own README.md, which Cargo uses as the package readme, and a copy of the repository LICENSE, so that every archive carries the MIT license text. Both copies must equal the root LICENSE.

    Versioning¶

    The Rust bindings have their own version, independent of OpenTLV Core:

    • The first standalone Rust release is 0.1.0. The inherited 0.7.1 was an unpublished migration baseline, not a previous Rust release. There were no Rust repository tags or GitHub releases when checked on 2026-10-27. The Rust version is independent of Core's 0.8.0 dependency version.
    • Both crates always have the same version, the single [workspace.package] version, and are released together. Cargo.lock records it for both.
    • Versions follow SemVer as Cargo applies it. Before 1.0, a breaking change of either crate's public API, Cargo features, native linking contract or minimum supported Rust version increments the minor version; any other change increments the patch version.
    • Changing the Core lock in core/core-artifact.json always produces a new version, because the lock determines the Core that each build of a published version uses. It increments the minor version when the Core change breaks one of the contracts above.

    Version relationship¶

    opentlv depends on exactly the opentlv-sys version it is released with:

    opentlv-sys = { version = "=0.1.0", path = "../opentlv-sys", default-features = false }

    The exact requirement is deliberate. links = "tlv" permits only one opentlv-sys in a dependency graph, the CI tests the two crates only as a pair, and the opentlv-sys version identifies the Core dependency, so a caret requirement would allow untested combinations with a different Core. Inside the workspace, Cargo uses the path; in the package, Cargo removes the path and keeps the version requirement.

    Core compatibility¶

    Each opentlv-sys version pins exactly one Core dependency, recorded in core/core-artifact.json, which is part of the package:

    Crates Core version Core commit Core release
    0.1.0 0.8.0 345c77acb29266036df5f27d04ce315bb61853cc v0.8.0

    The packages do not contain Core. A build from an archive selects Core exactly as a build from the repository does, as described in the README: it authenticates the locked Core release and selects its compatible static binary or builds its verified source. opentlv::version() reports the version of the Core library actually linked at run time, which can differ from the pinned one when OPENTLV_LIB_DIR links a prebuilt library.

    Package contents¶

    Each .crate archive contains exactly the crate's tracked files plus Cargo's generated Cargo.toml, Cargo.toml.orig, Cargo.lock and .cargo_vcs_info.json:

    Crate Files
    opentlv-sys README.md, LICENSE, build.rs, src/, the native integration files in core/ (lock, selection module, release verifier and CMake toolchain probe) and the tests with the C ABI probes in tests/abi_probe/ and tests/compose_abi_probe/
    opentlv README.md, LICENSE, build.rs, src/, tests/ and the eleven examples

    The build scripts and tests read only files inside their own package, the Cargo OUT_DIR, the selected Core tree and their own temporary directories. The only local path in a manifest is the declared opentlv-sys workspace dependency, which carries a version.

    Validation¶

    The package check of scripts/ci.py, part of the stable CI configurations, runs cargo package --workspace --locked, which builds both crates from their archives. It requires the exact file lists above, a LICENSE equal to the repository license and, in each archive's normalized Cargo.toml, the crate name, the workspace version, MIT, the README.md readme, this repository URL, no dependency path and the dependency opentlv-sys = "=<version>" for opentlv only. tests/test_packaging.py checks the manifests, the shared version, the unchanged features against the migration baseline, the license copies and the Core compatibility table without building.

    To inspect the packages locally, from the repository root:

    cargo metadata --format-version 1 --no-deps
cargo package -p opentlv-sys --list
cargo package -p opentlv --list
cargo package --workspace --allow-dirty

    cargo package -p opentlv alone fails, even with --no-verify, while opentlv-sys is not on crates.io: Cargo resolves an unpublished dependency from a local archive only for crates packaged in the same invocation. Use --workspace, as CI does.

    Licensing¶

    Both crates declare the SPDX expression MIT in license and carry a LICENSE copy equal to the root LICENSE, which names Marek Cingel as the copyright holder. Packaged Rust, Python and CMake sources keep their SPDX headers. The repository's REUSE.toml and LICENSES/ are not packaged: in an archive, the crate LICENSE covers the files without a header, which are the README, the Core lock, the C ABI probe's CMakeLists.txt imported from Core and Cargo's generated files. Neither crate has Cargo dependencies beyond opentlv-sys, and no third-party code is vendored.

    The archives contain no Core sources. opentlv-sys authenticates the pinned Core release at build time, or links a library selected with OPENTLV_LIB_DIR, and the resulting tlv library becomes part of the Rust binary. At the pinned commit, Core's LICENSE is byte-identical to this repository's and its library sources carry only MIT and Copyright (c) 2026 Marek Cingel notices. A binary distribution therefore needs that one MIT notice; recheck Core's licensing notices when changing the pinned commit, and add the license of every new bundled or linked dependency here and to the crate archives.

    GitHub release¶

    The manual Rust Release workflow accepts an unused vMAJOR.MINOR.PATCH tag matching both Cargo manifests, Cargo.lock and ci/release-notes.md. Changes stay under Unreleased during development; close the changelog under the matching version without the tag's v prefix and the release date before dispatching the release (for example, ## [0.1.0] - 2026-10-28). The versioned release notes are the publication text and are included in the hashed CI definitions. No crates.io credentials or uploads are involved.

    1. Review and merge the release preparation. Wait for successful Rust Main CI on that exact commit. Dispatch Rust Release on main with tag: v0.1.0.
    2. The workflow rejects a foreign, dirty or non-main checkout, a changed main tip, an existing tag/release, wrong versions or missing Main evidence. It runs Full CI with require_verified_core: true: all seven configurations, source quality, CodeQL, API coverage, packaging and the aggregate gate.
    3. Assembly revalidates every record against the current commit, run, attempt, Core lock and source hashes. It copies the exact two Linux stable packages whose digests the Full record contains. It does not rebuild them.
    4. The workflow attests all five assets: opentlv-sys-0.1.0.crate, opentlv-0.1.0.crate, release-manifest.json, release-notes.md and SHA256SUMS. Publication rechecks evidence, checksums, attestations and unused tag status, then creates the tag and a draft release. Only after the uploaded asset names, sizes, SHA-256 digests, notes and tag commit match does it publish the draft and verify the public result.
    5. Record the published URL and exact commit, Main and Release/Full run links in issue #33 and Core epic #718. Close the tracking only after publication and asset verification. The workflow emits rust-published-<attempt> with the URL, source and asset identities.

    If a failure occurs after creating a tag or draft, inspect that state before retrying; the workflow deliberately refuses to overwrite either. Earlier attempts' artifacts cannot satisfy a new attempt. A new main commit or a new Main run requires a new release attempt with matching evidence.

    For GitHub release archives before crates.io publication, extract both .crate files into adjacent directories, then use a Cargo path dependency and patch the exact registry dependency back to the extracted raw crate:

    [dependencies]
opentlv = { path = "vendor/opentlv-0.1.0" }

[patch.crates-io]
opentlv-sys = { path = "vendor/opentlv-sys-0.1.0" }

    The normal Core build requirements still apply. Rust's crate version is 0.1.0; opentlv::version() should report linked Core 0.8.0.

    Remaining crates.io prerequisites¶

    These are not part of this preparation and must be resolved before or at the first publication:

    • Names and owners. Neither opentlv nor opentlv-sys existed on crates.io on 2026-10-22. The first publication claims both names; crate owners, such as an OpenTLV GitHub team, are set then.
    • Order. opentlv-sys must be published before opentlv, whose exact requirement must resolve from the registry.
    • Core availability. A build needs CMake, a C99 compiler, Python 3.11, an authenticated GitHub CLI and network access to GitHub. The locked Core v0.8.0 release assets and attestations must remain available. A compatible Verified Binary avoids compiling Core; otherwise the verified source is built locally.
    • docs.rs. docs.rs builds without network access, so the default build script cannot fetch Core there. Rendering the documentation on docs.rs needs a documentation-only build path in build.rs.
    • Documentation. The crate-level Rustdoc, the crate READMEs and the user guide describe a path dependency on an opentlv-rust checkout. They need the crates.io dependency once the crates are published.
    • Registry process. A crates.io token or trusted publishing configuration and a registry-specific publish gate remain to be defined. The GitHub release workflow publishes source packages only to GitHub Releases.

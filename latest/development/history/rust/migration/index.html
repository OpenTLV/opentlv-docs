    Rust migration record¶

    Historical record

    This page preserves a historical snapshot, including its original commands, paths and validation results. Those results describe the recorded review, not a current verification. For current instructions, see the current Rust development guide. See historical records for context.

    This document records the historical baseline and the #1 import. The standalone build of #2 later changed opentlv-sys/build.rs, opentlv-sys/tests/fixed_abi.rs, opentlv/tests/corpus.rs and opentlv/Cargo.toml so that they reach Core through a pinned dependency instead of ../../... It preserved the crates, features, linking modes, API, tests, examples and the frozen inventory. The layout normalization of #5 then moved the workspace from bindings/rust/ to the repository root. The inventory and this record keep the original bindings/rust/ paths, which are Core's source paths and those of the import commit. The documentation integration of #6 turned the imported guides into the current standalone user guide and development guide; the import commit and the pinned Core links below keep the originals. Use the README to build and the standalone build validation for its results. To verify the original import, rather than today's working tree, against this record:

    python -B scripts/verify_migration.py --core ../opentlv \
  --import-ref 95d6299099af7a7d774ed89ee223f2cda5035aa9

    This record fixes the pre-migration state of the Rust bindings in Core for OpenTLV/opentlv#671, part of the Rust binding migration epic. It is the reference for every later migration step. The baseline sections below describe the state before any Rust source was imported and stay unchanged. The source transfer for opentlv-rust#1 is recorded in Source import and compared against this baseline.

    Crate default Features

    In source builds, the three features set OPENTLV_LLDP, OPENTLV_NFC and OPENTLV_DOCUMENT. The build script always enables OPENTLV_READER, OPENTLV_WRITER, OPENTLV_QUERY, OPENTLV_SCHEMA and OPENTLV_CODEC, and passes no OPENTLV_FORMAT_* or OPENTLV_EMV options. In Rust code, document gates Document, DocumentBuilder, DocumentError, Node, NodeMut, the Query edit API and document-dependent Program paths; lldp and nfc gate Format::Lldp and Format::NfcType2.

    Native linking modes¶

    Mode Selection Behavior
    Source build (default) OPENTLV_LIB_DIR unset build.rs configures ../../.. (the Core root) with CMake into OUT_DIR, always as a Release static, position-independent library without C++, tests, examples or warnings-as-errors, and links static=tlv
    Prebuilt static OPENTLV_LIB_DIR=<dir>, OPENTLV_LINK_KIND=static Links static=tlv from <dir>
    Prebuilt shared OPENTLV_LIB_DIR=<dir>, OPENTLV_LINK_KIND unset or dylib Links dylib=tlv; the loader must find the library at run time

    Prebuilt libraries must be built with components matching the enabled Cargo features. Any other OPENTLV_LINK_KIND value fails the build script. The build script reruns when OPENTLV_LIB_DIR, OPENTLV_LINK_KIND, or Core's CMakeLists.txt, cmake/ or tlv/ change.

    Supported platforms and toolchains¶

    The documented requirements are Rust 1.70 or newer, CMake 3.16 or newer, a C99 compiler and, on Windows, the MSVC Rust toolchain with Visual Studio.

    The original workflow uses the current stable Rust toolchain. It runs on main pushes, version tags and pull requests touching bindings/rust, tlv, tests/fuzz, tests/query, cmake, any CMakeLists.txt or the workflow:

    • cargo fmt --all --check and cargo clippy --workspace --all-targets -- -D warnings on Ubuntu 24.04;
    • cargo build --workspace --all-targets, cargo test --workspace, the quick_start example and the shared Query corpus through query_conformance with RUSTFLAGS=-D warnings on Ubuntu 24.04, adding Windows and macOS on release tags.

    It uses only default features and the source-build linking mode. It does not check the declared rust-version, reduced features, prebuilt linking or Rustdoc. This describes the preserved workflow, not evidence that every platform passed at the source commit.

Each configuration used its own CARGO_TARGET_DIR under the ignored build/671/ directory of this repository, so no existing build output was reused. Every Cargo command except Rustdoc ran with RUSTFLAGS=-D warnings. The Core worktree was still clean after the run.

    Known baseline failures¶

    • Prebuilt shared library on Windows MSVC. Linking the tests and the quick_start example fails with LNK2019 for the data symbols tlv_format_ber, tlv_format_emv, tlv_format_cer, tlv_format_der, tlv_format_lldp and tlv_format_nfc_type2. opentlv-sys declares them as extern statics without a #[link(name = "tlv", kind = "dylib")] attribute, so rustc does not import them through __imp_ symbols from the DLL import library. Functions link correctly. This is pre-existing: the original workflow never exercises prebuilt linking. Linux and macOS were not tested. The migration preserves this behavior. Any fix is separate work and must not be mixed into the source transfer.
    • Rustdoc intra-doc links. Three links in opentlv/src/codec.rs (lines 548, 851, 861) of the form [`CodecFailure::from(crate::Error::...)`] do not resolve. Rustdoc still succeeds; the original workflow does not build Rustdoc.

    Observations¶

    • An earlier attempt with a deeper target directory failed every source build before Rust compilation. MSBuild could not create a 245-character CMake try-compile .tlog path; Windows long paths are disabled on this machine. Core's in-tree bindings/rust/target stays below the limit. The run was repeated from scratch with a shorter build root. A standalone layout that nests Core builds more deeply can hit this limit on Windows.
    • The C ABI probe test creates its CMake build directories under the system temporary directory, not Cargo's target directory.
    • Rust links with the newest installed MSVC linker (14.50.35717, Visual Studio 18), while the source-built Core library used the CMake-selected Visual Studio 17 2022 toolset. This mix linked and passed.

    The machine-readable report records exact commands, working directories, environment overrides, exit codes, durations, per-target test counts and log hashes. The compact log keeps test summaries, example and Query output, Rustdoc warnings and the link errors. Full logs remain in the ignored local build/671/ directory.

    The declared rust-version 1.70, Linux, macOS, 32-bit targets, other feature subsets and hosted CI were not tested. These results establish the baseline in the original Core build context, not standalone build readiness.

    Recorded metadata discrepancies¶

    These are recorded as they are and are not changed by the migration baseline:

    • Both crates are versioned 0.7.1, the same as Core, although the development guide describes the crate version as independent and gives 0.1.0 as an example.
    • repository metadata and several guide links point to https://github.com/marekcingel/OpenTLV.
    • The Rust guides document the lldp and document features but not nfc.

    Verifying the baseline¶

    With a sibling Core checkout that contains the source commit:

    python -B scripts/verify_baseline.py --core ../opentlv

    The verifier confirms that the commit is retrievable and that the inventory matches the complete bindings/rust tree plus the explicit workflow and guides. It checks each Git blob ID, SHA-256 hash and size, the recorded history range, workspace metadata, locked crate versions, crate metadata and Cargo features. It does not build or run anything. Checks on temporary copies confirmed that it rejects a changed hash, a missing inventory entry, a changed feature default and a changed history count. Later migration steps should be compared against this frozen inventory rather than updating it to hide changes.

    Reproducing the runtime baseline¶

    From a clean Core checkout at the source commit, run each command in bindings/rust with CARGO_TARGET_DIR set to a fresh, short directory outside the Core tree and RUSTFLAGS=-D warnings:

    cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo build --workspace --all-targets
cargo test --workspace
cargo run -q -p opentlv --example quick_start   # likewise parse, reader, validate, write, writer
python -B ../../tests/query/run.py --native "$CARGO_TARGET_DIR/debug/examples/query_conformance" --property-cases 0
cargo doc --workspace --no-deps                 # without RUSTFLAGS
cargo test --workspace --no-default-features    # separate target directory

    For the prebuilt modes, build Core's tlv target with CMake using the options listed in build.rs, all three feature components on, and OPENTLV_BUILD_SHARED_LIBS set to OFF or ON. Then run cargo test --workspace with OPENTLV_LIB_DIR pointing at the library directory and OPENTLV_LINK_KIND set to static or dylib. For dylib, also add that directory to the loader path. validation.json has the exact commands.

    Preserved contracts¶

    • Both crates, their names, versions (0.7.1), metadata and the Cargo.lock are unchanged.
    • Public Rust API, FFI declarations, ownership and lifetime behavior are unchanged.
    • Cargo features lldp, nfc and document, and their defaults, are unchanged.
    • build.rs and all three native linking modes are unchanged, including the known prebuilt shared-library failure on Windows MSVC.
    • Unit, integration, doc and ABI probe tests and all seven examples are copied without changes.
    • The generated diagnostic vocabulary files are copied as they are; their generator stays in Core.
    • No Core file is changed or removed.

    Migration-specific differences¶

    These are the only changes outside the imported files:

    • The workspace stays at bindings/rust/. Keeping the original layout keeps every Core-relative path in build.rs, fixed_abi.rs and corpus.rs unchanged. Layout normalization is opentlv-rust#5.
    • The original workflow is kept as docs/migration/original-rust.yml. It is historical evidence, not an active workflow; standalone CI is opentlv-rust#3.
    • .gitignore ignores /bindings/rust/target/, as Core does for the same path.
    • The README, this record, the changelog and scripts/verify_migration.py are new.

    The imported workspace still resolves Core through ../../.. from its crates. In this repository that is the repository root, which has no Core sources, so the source build, the C ABI probe and the corpus seed replay do not work here yet. Do not run Cargo in bindings/rust before the standalone build and verified Core dependency of opentlv-rust#2 exist.

    The preserved guides describe the original Core checkout. Their commands and links to other Core documents keep that context and are not standalone instructions. For working cross-links, use the pinned user guide and developer guide. Documentation integration is opentlv-rust#6, which has since replaced the imported guides with standalone instructions.

    Verifying the import¶

    With a sibling Core checkout that contains the source commit:

    python -B scripts/verify_migration.py --core ../opentlv

    The verifier first runs the baseline verification. It then compares every imported file byte-for-byte with its original Git blob and with the SHA-256 hash and size in the frozen inventory, and rejects missing, extra or modified files in bindings/rust. Only Cargo's bindings/rust/target/ is ignored. It does not build or run anything. Checks on temporary copies confirmed that it rejects a modified source file, an extra file in bindings/rust and a missing guide, and accepts Cargo build output.

    Known limitations and follow-up work¶

    These are outside the migration and are tracked separately:

    • Verified Core. No approved Core release with schema-2 assets exists, so the lock has no release tag and Verified Source and Verified Binary selection, including GitHub Artifact Attestation verification, has not run against a real release. Lock one once it exists.
    • Core pin. The lock stays at the migration source commit, which still contains Core's former bindings/rust. Moving it past the cleanup is a normal reviewed dependency update.
    • Windows shared linking. Prebuilt shared linking on Windows MSVC still fails on the data symbols recorded in the baseline.
    • CodeQL. Full reports that CodeQL Action v3 is deprecated in December 2026; rust-codeql.yml needs v4.
    • Deferred by the migration epic. crates.io publication, a release workflow, Cargo feature normalization and API evolution.

    JS/WASM package preparation and publication¶

    The canonical package.json defines the independent @opentlv/opentlv version. The first standalone release is 0.1.0 (#32), prepared against Core v0.8.0; 0.2.0 is the first npm registry version (#40). The next patch, 0.2.1, contains release recovery fixes (#47) with the same Core pin. The earlier 0.1.0-dev.0 was an unreleased development identity, not a previous JS release; there were no JS repository tags or GitHub releases when checked on 2026-10-28. The JS version is not the pinned Core version: change it explicitly when advancing the binding; a Core pin change never changes it automatically. Record binding changes under Unreleased in CHANGELOG.md.

    Release tags are vMAJOR.MINOR.PATCH and must equal v plus the package.json version, the component_version in docs-examples.json and the heading of ci/release-notes.md. Prerelease tags and npm dist-tags are not used.

    The approved publication change (#40) removed private: true, which makes npm refuse publication, as described in the npm package metadata contract. Package checks now reject any private field. The GitHub release workflow attaches the tested archive to a GitHub release. Its optional npm publication publishes that same archive after an explicit approval, and verification checks a published version against it. No registry credential or lifecycle hook is added.

    Package identity¶

    The package is @opentlv/opentlv, selected in #37 and checked on 2026-10-30:

    Item Decision Evidence
    Organization opentlv The public registry lists the scope with no packages (/-/org/opentlv/package returns {})
    Owner npm account marekcingel Recorded by the maintainer in #36; the registry does not show it without signing in
    Package name @opentlv/opentlv The registry has no such package (404), so nothing has been published under it
    Access Public once published Scoped packages need an explicit --access public

    The scope limits who can publish, while the package name is created only by its first publication. Selecting the name therefore published nothing and changed no access: private: true stayed until the approved publication change (#40); on 2026-11-02 the registry still returned 404 for the package. The release workflow and the manual first version pass --access public on the command line (#39), so publishConfig remains rejected. Whether the organization enforces 2FA for all members still has to be confirmed in its npm settings (setup step 5); it is not visible from the public registry.

    opentlv-js remains the name of the repository, its CMake targets and the migration owner. Imports use @opentlv/opentlv, and npm pack names the archive opentlv-opentlv-<version>.tgz. The v0.1.0 GitHub release predates this selection: its asset stays opentlv-js-0.1.0.tgz and is imported as opentlv-js.

    Build and check¶

    Activate Emscripten 4.0.10, Node 22 (including npm) and TypeScript 5.9.3 (tsc on PATH), and provide Chrome or Chromium (google-chrome, chromium or chromium-browser on PATH, or OPENTLV_BROWSER set to its path), then run:

    emcmake cmake -S . -B build-wasm -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-wasm --target opentlv-wasm --parallel
ctest --test-dir build-wasm --output-on-failure --no-tests=error
python -B scripts/package.py --build build-wasm --output build/package-check

    Use the default pinned Core build. The command verifies its live source receipt and rejects sibling development overrides. It checks all four nonempty outputs in <build>/dist/, the WASM header and wrapper equality with src/*.mjs. It runs the smoke, Format/field and Reader/Writer streaming suites and their parse, fields and streaming examples against the installed package. It also runs the Document/Schema suite and example, and compiles the installed TypeScript consumer with strict NodeNext and Bundler resolution, without the DOM library. These checks establish local package consistency, not attestation of arbitrary prebuilt binaries. CI builds the inputs afresh before packaging.

    The output directory must be new. The script stages an exact file allowlist, generates version.mjs from package.json, and runs npm pack first with --dry-run, then as a local archive. Both calls use --offline --ignore-scripts. The actual archive must contain exactly the expected regular files, with the expected SHA-256 bytes; missing, extra, duplicate and symlink entries fail.

    It then installs the archive into an isolated consumer using offline npm with scripts, audit and funding requests disabled. The consumer checks every public export, the independent version, the preserved Core version, WASM asset lookup, default/explicit loader locations and parsing. The original smoke/parse checks and the generic field/streaming suites and examples run against the installed archive. CI also runs the Core-owned Query fixtures through the installed package's original facade runner.

    The check then repeats the install and consumer test in a clean project outside the checkout. Its path contains a space and a non-ASCII character, its working directory is that project, and NODE_* and npm_* settings and the user's home are not inherited. The TypeScript checks run there, so the checkout's node_modules cannot satisfy them.

    tests/package_browser.mjs serves the installed package from a local HTTP server and loads it in headless Chrome, as a module page using the documented import map and as a module worker. Each loads the WASM from its adjacent default and from a separate locateFile URL, then parses and encodes a Document. The result records the browser version. CI uses the Chrome preinstalled on the runner, so its version follows the runner image.

    The source checkout is a metadata/build source, not an installable package: generated index.mjs, version.mjs and dist/ live only in the staging area. Do not pack or install the source root directly. For local experimentation, install the checked build/package-check/opentlv-opentlv-<version>.tgz archive. The exact archive name, hashes and commands are in build/package-check/result.json.

    API and evidence¶

    The package README describes each export and asset location. The four original runtime filenames remain unchanged; API additions are tracked separately from the immutable migration baseline. packaging/index.mjs re-exports the existing facade and adds packageVersion. The @opentlv/opentlv/version subpath exposes that value without loading the facade. Existing (await loadOpenTLV()).version and the C bridge version entry point continue to identify Core, preserving their migration contract.

    package-info.json includes binding identity and separate immutable Core source identity/output hashes. It excludes machine-specific build paths so identical builds can produce identical packages. Node 22 is the validated runtime; ESM is the only package module interface. The exact 22-file archive includes five .d.mts declarations, with types exports for every JavaScript entry point. TypeScript 5.9.3 checks both NodeNext and Bundler resolution; this does not establish bundler runtime compatibility. Browser and worker evidence is the headless Chrome check above; other browsers, bundlers, CommonJS and CDN support are not claimed.

    The package keeps license: "MIT" for original binding code and includes the root LICENSE, LICENSES/MIT.txt, THIRD_PARTY.md and four upstream notices/ files for Core, Emscripten, musl and compiler-rt. The generated version.mjs has the binding's SPDX/author header. Runtime JS/WASM retains its upstream ownership; the package MIT field does not replace those terms. Missing, empty or symlinked notices fail staging, and archive/installed-consumer checks verify their exact bytes. Keep notices with copied runtime assets. See dependency attribution before changing Core or toolchains.

    All CI tiers run package checks. The double-build tier in Full CI also compares the complete archive hash, metadata and file hashes across two independent builds and uploads the first build's archive as js-package-<attempt>. Package reports keep published and release_verified false: they are build results. A passing local run does not establish hosted CI or a verified release.

    GitHub release¶

    The manual JS Release workflow (js-release.yml) accepts an unused tag matching the versions above. Changes stay under Unreleased during development; close the changelog under the matching version without the tag's v prefix and the release date before dispatching the release (for example, ## [0.1.0] - 2026-10-28). The release rejects a changelog without that section. The versioned release notes are the publication text.

    1. Review and merge the release preparation. Wait for successful JS Main CI on that exact commit. Dispatch JS Release on main with tag: v0.1.0.
    2. scripts/release.py prepare rejects a missing, unprefixed or otherwise malformed tag, a foreign, dirty or non-main checkout, a dispatch from another workflow revision, a changed main tip, an existing tag or release, differing versions, notes or changelog, a Core lock that is not an exact v release tag commit (currently Core v0.8.0), and missing or failed Main CI, including its JS quality gate (#34).
    3. The workflow then runs Full CI in the same attempt: Release and Debug, the double-build reproducibility tier, migration compatibility, package checks and both quality gates.
    4. Assembly revalidates the request and every Full record against the commit, run, attempt and Core lock. It copies the exact opentlv-opentlv-<version>.tgz whose SHA-256 and file hashes the reproduced builds recorded; it does not rebuild it. The workflow attests all four assets: the archive, release-manifest.json, release-notes.md and SHA256SUMS.
    5. Publication rechecks evidence, checksums, attestations and the tag state, then creates the tag and a draft release through the GitHub REST API. It retains the returned release ID for uploads, verification and publication; an absent entry in a delayed releases list does not lose that identity. Only after names, sizes, SHA-256 digests, notes and tag commit match does it publish the draft and verify the public result. js-published-<attempt> records the release ID, URL, publishing identity, original payload identity and assets.
    6. Record the published URL, exact commit, Main and release run links in issue #32 and Core epic #718. Close the tracking only after publication and asset verification.

    Recover an interrupted GitHub publication¶

    Use Re-run failed jobs in the original JS Release run. The publish job selects exactly one assembled js-release-<attempt> artifact from that run and revalidates its original Full attempt, current Main evidence, source, Core pin, checksums and attestations. It allows a later publishing attempt of the same run and commit; it does not substitute a new build or another run's evidence.

    Every publishing attempt keeps a journal, build/publish-state/draft.json, uploaded as js-draft-<attempt> even when the job fails. The journal is written before the first write and again just before the draft is requested. Once GitHub returns a valid draft object, it records that draft's release ID before any upload. A retry downloads the journals of the run and finds the draft only by that recorded ID. The releases list can lag behind a creation, so it serves only to detect conflicting or duplicate releases.

    • If only the tag exists at the verified commit and a journal shows that no draft was requested, create the draft.
    • If a journal records a release ID, read that release by ID and require the exact local payload's asset names, sizes and SHA-256 digests, notes and tag commit before publishing it.
    • If that exact release is already public (for example, the previous job lost its response after publication), verify it and emit the receipt without writes. Without a recorded ID, only the exact release-by-tag endpoint, which serves only published releases, can identify it.
    • If a draft was requested but no ID was recorded (lost or malformed response), or the tag exists without any journal of the run (lost runner), an unlisted draft may exist: stop without creating another one.
    • If the draft has partial uploads, unexpected or duplicate assets, different bytes or metadata, or the tag points elsewhere, stop without replacing, deleting or retargeting anything. Record the run, tag, release ID and asset metadata for maintainer review. Any manual cleanup requires a separate decision.

    A new dispatch still requires an unused tag. Do not use Re-run all jobs for publication recovery: multiple assembled payloads are ambiguous and rejected. A changed main tip or Main evidence also stops recovery. A new release requires fresh preparation and Full CI; it cannot reuse a previous version's evidence. If npm has already published, retry only its failed verification job as described below. No workflow has a tag-push trigger, so a tag cannot bypass these gates.

    Since 0.2.0, install the package from npm with npm install @opentlv/opentlv. To use a downloaded release archive instead, check it against SHA256SUMS and its attestation first:

    gh attestation verify opentlv-opentlv-<version>.tgz --repo OpenTLV/opentlv-js
npm install ./opentlv-opentlv-<version>.tgz

    The archive contains the four runtime files, so consumers do not need Emscripten or Core. packageVersion reports the package version, for example 0.2.0; the existing (await loadOpenTLV()).version reports the embedded Core 0.8.0.

    package-info.json stays outside the export map; read it from the installed package directory. The audit listed what registry publication still had to change; #40 resolves it as follows:

    • The packaged README installs from npm instead of the archive and no longer says that the package is not on the registry.
    • engines stays at 22.x, the only tested Node version. Other versions get an npm warning, not a refusal.
    • Organization-wide 2FA enforcement is confirmed by the maintainer in setup step 5; the public registry does not show it.

    npm publication¶

    The npm input of JS Release (#39) publishes the GitHub release archive of the same run to npm as @opentlv/opentlv. Nothing is rebuilt: npm receives the bytes that Full CI reproduced and tested and that the release attested. Pull requests, Main, Full and manual Full runs cannot publish.

    Protection How
    Explicit approval The npm job uses the GitHub environment npm, which must require a reviewer, deploy only from main and not let administrators bypass it
    No registry token npm trusted publishing accepts an OIDC token only from this repository, js-release.yml and the npm environment. Besides release attestation, only this job has id-token: write
    Immutable archive The job publishes opentlv-opentlv-<version>.tgz from the release assets after rechecking the manifest, Full evidence, checksums, attestations and the public GitHub release
    One version, once npm versions cannot be replaced: a version that npm already has with other bytes fails, and a new version must be newer than latest
    Provenance npm generates SLSA provenance for trusted publishing from a public repository. The job requires it to name the archive's SHA-512, this workflow on main, the release commit and the run

    Preflight rejects npm: true before Full CI starts if package.json still has private: true, the environment lacks any of its protections, the package does not exist on npm yet, or the version is not newer than npm's latest. #40 removed private: true; until the first version exists on npm, an npm request still fails and names the manual first version. The request records the npm state it saw, so assembly and GitHub publication fail if that state changes.

    After the GitHub release is public, the npm job waits for approval. The approved job then:

    1. Installs npm 11.21.1 on Node 22. Trusted publishing needs npm 11.5.1 and Node 22.14 or later; npm 12 would need Node 22.22.2.
    2. Runs scripts/publish_npm.py prepare. It takes the original attested release assets identified by the GitHub publication receipt and verifies them as the GitHub publication did: request, Full records and gates, checksums, notes and the attestation of each asset. The public release and tag must hold exactly these assets, the environment must keep its protections, and the run must record an approval of npm. The archive's package.json must name @opentlv/opentlv, the release version and this repository, without private.
    3. Runs npm publish ./build/npm/opentlv-opentlv-<version>.tgz --access public --provenance --tag latest --ignore-scripts against https://registry.npmjs.org/. If npm already has the version with the same SHA-512 and SHA-1, it publishes nothing and only confirms.
    4. Runs scripts/publish_npm.py confirm. It waits until npm serves the version as latest with the archive's integrity and provenance, and checks the provenance statement. It then installs the version from the registry into a clean project, compares the lockfile integrity and runs npm audit signatures.
    5. Uploads js-npm-<attempt> with plan.json and receipt.json. The receipt names the npm URL, GitHub release, commit, run, integrity, provenance run and the approving reviewers.

    If the approval is rejected or the npm job fails, use Re-run failed jobs. The GitHub release and its tag remain, so a new dispatch of the same tag fails. The re-run downloads the earlier attempt's assets, verifies them again and asks for approval again.

    Setup and first version¶

    npm can configure trusted publishing only for an existing package. The maintainer therefore publishes the first version once, from the attested release asset; later versions use the workflow:

    1. In the repository settings, create the environment npm: add a required reviewer, disallow administrator bypass, limit deployment branches to the single branch rule main, and add no secrets or variables.
    2. In the approved publication change, remove private: true, choose a new version and update the packaged README. #40 did this for 0.2.0.
    3. After merging it and a successful JS Main CI on that commit, dispatch JS Release on main with tag: v0.2.0 and npm: false. After it publishes the GitHub release, download its assets and run sha256sum -c SHA256SUMS and gh attestation verify opentlv-opentlv-0.2.0.tgz --repo OpenTLV/opentlv-js. Then publish the archive from an npm account with 2FA: npm publish ./opentlv-opentlv-0.2.0.tgz --access public. This version has the GitHub attestation but no npm provenance.
    4. Check that npm view @opentlv/opentlv@0.2.0 dist.integrity equals the archive's SHA-512 as sha512-<base64>, then verify the published version with --unattested and record its verification.json in #40 and #36.
    5. In the package settings on npmjs.com, add a GitHub Actions trusted publisher for OpenTLV/opentlv-js, workflow js-release.yml and environment npm, and allow npm publish: configurations created since 2026-09-03 allow only staged publishing by default. An unused configuration expires after two days, so add it shortly before the next npm release. Then select Require two-factor authentication and disallow tokens under publishing access, and confirm that the opentlv organization enforces 2FA.
    6. Dispatch later releases with npm: true, and verify each published version without --unattested.

    Direct publishing and configuration evidence (#47)¶

    This workflow deliberately uses direct npm publish of the attested tarball, with approval in the protected GitHub npm environment before it runs. npm's staged publishing is a separate review/promotion flow and is not implemented here. Keep the publisher's npm publish permission enabled; its additional npm stage publish permission does not make this workflow staged. No separate npm dist-tag command is used.

    The 2026-11-03 walkthrough in #47 records maintainer screenshots of the publisher identity OpenTLV, opentlv-js, js-release.yml, npm. It also records environment selections: required reviewer marekcingel, self-review prevention off for the sole maintainer, administrator bypass off, only branch main, no environment secrets/variables. These are reported UI selections, not an independent API verification of the saved configuration. Release preflight checks the saved environment protections again. Retain OPENTLV_DOCS_DISPATCH_TOKEN: it serves Docs integration, not npm publication.

    Before the next release, retain evidence of the saved environment and its branch policies, npm organization-wide 2FA, package ownership/publisher permissions, and Require two-factor authentication and disallow tokens. Check repository, environment and applicable organization secret names for legacy npm tokens; never copy secret values into evidence. Publisher registration alone does not prove OIDC authentication or provenance.

    The issue reports a pending-validation deadline of 2026-11-05 11:28 UTC (12:28 Europe/Bratislava). Recheck npm settings before dispatch; if it has expired, configure it again for a genuine release. Do not publish a dummy version or weaken checks to meet the deadline.

    The changelog is closed as 0.2.1 with the preparation date; if the release is dispatched later, adjust that date before merging. Merge the reviewed preparation, wait for Main on that exact revision, then dispatch JS Release from main with tag: v0.2.1 and npm: true. Approve the protected environment. After success, retain js-npm-<attempt>/receipt.json and run:

    python -B scripts/publish_npm.py verify 0.2.1 --output build/npm-verify-0.2.1

    Link the configuration evidence, Main/release runs, public release, receipt and independent verification.json to #47, #36 and Core #716. First live OIDC publication and npm SLSA provenance remain pending until those checks pass; the manual 0.2.0 exception is not evidence for later releases. Keep #47 open until its remaining configuration and live-release criteria are verified.

    Local validation (#39)¶

    The Python infrastructure suite covers the environment protections, approvals, toolchain pins, the assets of the publishing attempt, rejected requests, archives and registry states, retries with the same or different bytes, provenance subjects, workflows, commits and runs, and the workflow structure. GitHub and the registry are mocked. The provenance checks follow the attestation of a published scoped package (@sigstore/core). No environment was created, no trusted publisher was configured and nothing was published. npm documents publishing a prebuilt archive, but its trusted publishing documentation does not show it, so the first workflow publication after the manual 0.2.0 verifies that path.

    Verify a published version¶

    scripts/publish_npm.py verify (#40) checks a version that is already on npm, however it was published, against its public GitHub release. It needs network access, Node 22 with npm, TypeScript 5.9.3 (tsc) and Chrome or Chromium as for the package checks, but no token, build or Core checkout:

    python -B scripts/publish_npm.py verify 0.2.0 --unattested --output build/npm-verify-0.2.0
    1. It downloads the assets of the public GitHub release v<version> and requires the expected asset set, the size and SHA-256 that GitHub records for each, matching SHA256SUMS, a manifest for this tag, version and notes, a tag on the released commit, and the archive SHA-256 and file hashes that Full CI tested. The attestations are still checked with gh attestation verify.
    2. npm must serve the version under @opentlv/opentlv with the archive's SHA-512 integrity and SHA-1, this repository and no private field, and latest must not be older.
    3. If npm lists provenance, it must name the archive, js-release.yml on main, the released commit and the release run. A version without provenance fails unless --unattested is given, and --unattested is rejected before any download for every version except 0.2.0, the manual first version (UNATTESTED in the script). Later versions without provenance always fail.
    4. It installs the version from the registry into a clean consumer outside the checkout, without inherited Node or npm settings and with a fresh cache. Every installed file must equal the tested archive. The consumer check, strict TypeScript NodeNext and Bundler checks, the installed Node suites and examples and headless Chrome then run against that installation.
    5. A second clean install records the lockfile integrity and runs npm audit signatures.

    It writes verification.json with the npm and GitHub release URLs, commit, release run, integrity, provenance, toolchain and browser, and the logs of every command, to the fresh output directory. It publishes and changes nothing.

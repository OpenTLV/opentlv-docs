    Lua releases¶

    Run Lua Release Gate (release.yml) manually from main. Its only input is tag, for example v0.2.0. Do not create the tag beforehand. The workflow selects the exact dispatch SHA, even if main advances during verification.

    Preparation¶

    1. Select an authenticated Core release produced by Core's current artifact workflow. Set its exact SHA in cmake/Core.cmake and the matching release/SHA in cmake/core-artifact.json. Verify the full Lua matrix after changing Core.
    2. Close the changelog and merge the candidate to main. The first release heading must match the tag, for example ## [v0.2.0] - 2026-10-19, followed by at least one change. No Unreleased occurrence is allowed. Keep the usual Unreleased section during development and close it only for release.
    3. Dispatch the gate from main with that tag. No alternate SHA or skip-verification input is available. Existing tags, including another version tag on the candidate, are rejected.

    The current Core artifact release is deliberately unset: the migration pin does not identify an available attested producer release. Preflight rejects this state. Ordinary development remains usable; it does not count as Verified Source. See the Core verification policy.

    Verification and publication¶

    Preflight locks the dispatch commit, Core release ID and authenticated manifest digest. Release calls Full CI in the same run: all 17 configurations, LuaRocks, sanitizers, static checks and CodeQL are required. Candidate workers create a private local tag so packaged metadata contains the intended release version; no remote tag exists yet. opentlv.version() and opentlv._VERSION report the same binding version as the packaged lua-version.json, without the tag's v.

    Always-running aggregate validation rejects missing, failed, cancelled, duplicate or skipped required evidence. The assembler revalidates the original request and dependency lock, actual test/package records and exact run attempt. It creates two tested Lua 5.4 module archives, a manifest and SHA256SUMS, then attests every file. The publisher verifies identities, digests, attestations and successful same-attempt jobs again before creating the tag and GitHub Release.

    Rerun all jobs when retrying: successful artifacts from an older attempt do not authorize publication. A service failure after tag creation can leave a tag without a complete release; inspect and recover manually. The workflow never overwrites an existing tag or release. A fresh dispatch rejects that tag.

    The publishing token does not trigger new workflows from its tag push. LuaRocks publication remains separate. No versioned release rockspec is generated by this gate; opentlv-scm-1.rockspec remains the development package.

    Automatic release documentation¶

    After GitHub confirms the release is published, the gate records its release ID, tag, exact Lua/workflow commits and run/attempt in release.json, uploaded as component-release-<attempt>. Notify Lua release documentation runs after the successful gate, verifies that publication succeeded in that attempt, then notifies Docs with component-release-published. It performs no checkout and executes no artifact code with the cross-repository credential.

    Merge the Docs receiver/configuration first. Configure OPENTLV_DOCS_DISPATCH_TOKEN with Contents write permission restricted to OpenTLV/opentlv-docs. Docs uses OPENTLV_COMPONENT_READ_TOKEN with Contents and Actions read access to the configured component repositories. It independently checks the trusted producer, attempt-scoped artifact digest, published release ID and tag/commit before publishing lua/<version>/, its version catalog and stable alias. Core/other component snapshots and development pins are preserved.

    Retry a failed notifier while its producer receipt is retained. Duplicate delivery reuses the immutable snapshot; old releases cannot move stable backwards. After receipt expiry, a newly verified producer receipt is required. Partial tag/release failures still require the manual recovery described above. Local mocked tests do not establish hosted notification or Pages deployment.

    The quality gate guide documents package compatibility, ownership, source fallback, CI timings and remaining hosted acceptance. Local fixtures cannot verify GitHub OIDC permissions or prove production publication.

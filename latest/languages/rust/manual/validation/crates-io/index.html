    crates.io identity and package validation¶

    Validation for issue #37 on 2026-10-30, against the assets of the v0.1.0 GitHub release at f297ab3899bafb95716a39a38dfaf7df14e8768d, built by run 40646933091, attempt 1. Nothing was published and no crates.io credential was used.

    Result¶

    The names are free, and the archives' metadata, license, dependencies and file lists are correct. These 0.1.0 archives must still not be published: see findings.

    crates.io does not reserve names, so anyone can claim either one until the first publication. That publication makes the publishing account the owner.

    The GitHub attestations API returns one SLSA provenance statement for each crate digest, from .github/workflows/rust-release.yml on refs/heads/main in that run. This reads the statement only; the signature was not verified locally.

    cargo publish --workspace --dry-run --no-verify --locked with Rust 1.99.1 from a clean v0.1.0 checkout, without a token, packaged both crates and aborted both uploads. It covers Cargo's client checks only. The crates.io server checks run at upload.

    Findings that block publishing these archives¶

    A published version cannot be changed, and these problems are inside the archives. The fixes need a new commit, so the first crates.io version must be a new version such as 0.1.1. Publishing different bytes as 0.1.0 would give one version two archives, because the GitHub release keeps its attested 0.1.0.

    1. Stale installation text. opentlv/README.md says the crates are not published and shows a path dependency, as does the crate documentation in opentlv/src/lib.rs. crates.io and docs.rs would display this text.
    2. docs.rs cannot build the crates. Building the documentation of the released opentlv-sys archive with DOCS_RS=1, offline and in a network namespace without network access, stops with Core dependency verification failed: gh is required to verify a Core release (exit code 101). build.rs has no documentation-only path. This simulates the docs.rs conditions; docs.rs itself was not used. No epic issue names this fix yet.
    3. Registry consumers need an authenticated GitHub CLI. A default build uses gh to authenticate Core, as the README states. Whether this requirement is acceptable for registry users is an input for issue #38.

    Changes¶

    • The CI package check now also compares each archive's description, keywords, categories, edition, rust-version, links, build script, features and publish with the expected registry identity. Applied to the real v0.1.0 archives, it accepts both.
    • The packaging document now lists tests/codec_abi_probe/, which the archive contains and the document omitted.

    Local validation¶

    Command Result
    python -B scripts/check_quality.py Passed, REUSE compliant with 163/163 files
    python -B -m unittest discover -s tests 103 tests passed
    scripts/ci.py build --tier pr --configuration linux-stable Could not run: the WSL host has no gh, so the first build stops at Core verification, and ci.py removes the development override

    No crate source, manifest, lock or workflow changed, so the PR tier's Cargo checks would not exercise this change. Hosted PR CI runs them. Full CI, which contains the package check, was not run locally; the real-archive check above covers the new comparison.

    Not verified¶

    • Publication permission and token scopes: no credential was used, and only a real first publication proves them.
    • The verified account email and GitHub organization access: the public API does not expose them, so they rest on the record in epic #36.
    • Publishing authentication and owner configuration, which belong to issue #39.
    • Consumer builds from the archives, which belong to issue #38.

    crates.io release validation¶

    Validation for issue #40, which owns the first crates.io publication. On 2026-11-01, nothing is published yet. The issue requires explicit approval first, so this record has the repository side and the steps left; the published results belong in Publication.

    The public crates.io owners endpoints returned HTTP 404 for both names on 2026-11-01. This is an availability observation, not a name reservation; the publication workflow checks again immediately before upload.

    Decisions¶

    The registry build findings needed these decisions before a version that cannot change:

    Finding Decision
    A default build needs a GitHub login, so a clean machine and docs.rs cannot build The Core lock records the SHA-256 of the release's SHA256SUMS. A build downloads the assets from the public release URLs and accepts them by digest. A logged-in GitHub CLI also verifies the attestations, and a failure stops the build. All CI tiers still require attested Core
    docs.rs has no network access With DOCS_RS, the build script selects and links no Core, and [package.metadata.docs.rs] documents all features for x86_64-unknown-linux-gnu
    Windows target directories are limited to 49 characters Shorter Core build directories raise the limit to 76
    The documentation describes a path dependency The crate READMEs, Rustdoc and user guide describe cargo add opentlv
    Verified Binaries are not selected in practice Unchanged: fixing it needs a new Core release. Consumers compile Core
    Cross compilation is not supported Unchanged, and now stated in the crate READMEs

    The version is 0.2.0, with the public API unchanged, because the v0.1.0 archives must not be published. The candidate was renamed from 0.1.1 to 0.2.0 on 2026-11-01. The build results and archive hashes below describe the earlier 0.1.1 candidate; publication requires fresh release evidence and archives for 0.2.0. After the version change, Cargo metadata and the release-version checks agree on 0.2.0, the old v0.1.1 tag is rejected, and all 66 release, publication and published-verification regression tests passed. git diff --check also passed.

    What the digest does and does not prove¶

    The lock is inside the crate, and crates.io never changes a published version, so the digest pins the exact Core assets for everyone who trusts that crate. It adds no trust of its own: unlike an attestation, it does not show on the user's machine who built the assets. The digest was taken from the public SHA256SUMS, whose listed manifest digest was compared, and every CI tier verifies the attestations of those same bytes.

    Not verified¶

    Only hosted runs and the publication itself can prove these:

    • Full CI with the consumer check on Linux, Windows and macOS, and the Rust Release and Rust crates.io workflows on GitHub, including everything the publication validation lists.
    • macOS builds without a login. Python from python.org needs its certificates installed for the public download.
    • The real docs.rs build, and scripts/verify_published.py against real answers. Its metadata fields were read from a real crates.io answer for libz-sys, and status.json from a real docs.rs answer for serde.

    Open steps¶

    Each is made by a maintainer, in this order. Steps 3 and 5 are the approval that the issue requires, and nothing in this repository takes them:

    1. Merge this change, including the changelog closed under ## [0.2.0] - 2026-11-01, as the release procedure requires.
    2. Wait for Rust Main CI on that commit, and keep main there until the publication.
    3. Dispatch Rust Release with tag: v0.2.0.
    4. Make the one-time configuration.
    5. Dispatch Rust crates.io with tag: v0.2.0, review the plan and approve the crates-io environment. This claims both crate names permanently.
    6. Finish the one-time configuration: add the trusted publishers, delete the secret and revoke the token.
    7. Record the results below, in a commit after the publication, and close the issue.

    Steps 4 and 6 are done: issue #45 recorded the trusted publishers, the revoked token and the deleted secret in the Trusted Publishing validation, and removed the token's path from the workflow.

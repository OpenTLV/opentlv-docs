# Development

Start with the documentation owned by the component you want to change.
The portal organizes the entry points; each repository maintains its technical
contracts, build instructions and release evidence.

For public processing contracts and native reference material, use
[API](../api/index.md). For application examples, start with
[Tutorials](../getting-started/overview.md).

## Architecture

Start with [Architecture](architecture/index.md) to find Core's canonical
explanations and the boundaries between execution, formats, Document, Query,
Codec, bindings and tools. Planned runtime work is identified separately.

## Building from source

Use [Building from Source](building/index.md) to choose Core, a binding, a tool
or the portal. Each repository owns its prerequisites and build commands.

## Contributing

Follow [Contributing](contributing.md) for repository policies and review
preparation. The [documentation ownership and portal conventions](documentation.md)
explain source ownership, the portal hierarchy and how historical migration
records relate to current guidance.

Use [Component contributor guides](components.md) for CLI, Lua, Python and Rust testing,
implementation and release procedures. Public API and installation chapters remain
in their language or tool manuals.

## Testing and quality gates

Use [Testing and Quality Gates](testing.md) for the PR/Main/Full/Release model,
test ownership and links to component validation. Performance and audit records
retain their original evidence scope.

## CI and release process

Read [CI and Release Process](releases.md) for component releases, reviewed
documentation pins, publication gates and immutable snapshots. Detailed release
and recovery instructions remain with each repository.

## Historical records

[Historical records](history.md) collects migration provenance, dated validation,
performance reports and completed audits. Current manuals remain the entry point
for setup and API use; the archive preserves the original evidence and owners.
